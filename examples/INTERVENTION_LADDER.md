# Intervention ladder — experiment driver

**Results, statistics and findings live in the companion evaluation project**,
which owns measurement for this repo:

- `benchmarks/intervention_ladder/RESULTS.md` — headline tables, all six
  conditions, bootstrap CIs and paired p-values
- `reports/intervention-ladder-evaluation.md` — full write-up

This file documents only what lives *here*: the task generator, the sweep
runner and the conditions.

## What the experiment is

The tool-scaling experiments found that tool count (6→100) and description
length (6.5x) cause no measurable degradation, and that the real variable is
chain length: past 5 steps the model silently skips steps it judges redundant.
Hierarchical routing was built as the mitigation.

This ladder tests interventions against that failure from free to expensive,
including the one nobody had tried — telling the model not to skip steps —
which mattered because `DEFAULT_SYSTEM_PROMPT` ends with *"when you have enough
information, respond with a final answer and do not call any more tools."*

Headline: only worked examples significantly improve exact tool-sequence match
(+17.8pp, p=0.0066); an abstract rule eliminates skipping but replaces it
one-for-one with unrequested calls; and the hierarchical arm's entire benefit
comes from an anti-skip sentence already present in `SUBAGENT_SYSTEM_PROMPT`,
not from the architecture. See the evaluation project for the numbers.

## Definitions

A **step** is one required tool call; **chain length** is the length of
`expect_tool_sequence`. Agent *turns* are not steps, and `max_steps` (20) is
set far above chain length so exhausting the loop budget can never masquerade
as skipping.

## `chain_task_gen.py` — task generation

Chains are generated by a random walk over a tool **type graph**
(`number → number`, `string → number`, `date → bool`, …); the walk holds a
current value and its type and may only take an edge whose input type matches.

**Ground truth is executed, never written.** Every tool in
`tool_scaling_kit.py` is a pure function, so after choosing a move the
generator calls the real tool and carries the real return value forward. The
expected sequence is whatever the walk took; the expected answer is whatever
the last call returned. Labelling cost is zero and labels cannot drift from
tool behaviour.

Chains are enriched toward five redundancy pressures reverse-engineered from
the original failure cases:

| Class | Definition |
|---|---|
| T1 no-op round | `math_round` on a value already at that precision |
| T2 inferable bool | a boolean the model can reason out unaided |
| T3 small stat | a sum/count/average over 3–5 single-digit numbers |
| T4 same tool twice | the same tool applied twice in a row |
| T5 identity round trip | `A` then `A⁻¹`, returning to the input |

Two calibration fixes worth knowing if you extend the generator:

- T1 was initially restricted to integer values, which starved it to 35% — any
  unit conversion earlier in a chain produces a float. Generalising to "round
  to the value's own current precision" (rounding 9.999975 to 6 places is as
  much a no-op as rounding 70 to 0) restored it to 78%, matching its dominance
  in the hand-written set.
- Trigger moves are weight-sampled; uniform choice let two-step moves (round
  trips, doubled tools) eat the step budget and T5 reached 82%.

Shipped corpus `gen_tasks_8step.json`: 60 tasks, 8 steps, 100% carrying at
least one trigger (T1 78%, T5 73%, T4 62%, T3 32%, T2 18%), 46 distinct tools.

## `intervention_ladder_test.py` — conditions and scoring

| Condition | Registry | Prompt change |
|---|---|---|
| `baseline` | flat, 100 tools | shipped `DEFAULT_SYSTEM_PROMPT` |
| `instruction` | flat, 100 tools | early-stop clause replaced by a completeness rule |
| `fewshot` | flat, 100 tools | `instruction` + two worked examples |
| `hierarchical_bare` | main + 5 specialists | specialist prompt's anti-skip sentence removed |
| `hierarchical` | main + 5 specialists | shipped `SUBAGENT_SYSTEM_PROMPT` |
| `hierarchical_fewshot` | main + 5 specialists | shipped + a tool-agnostic worked example |

Scored per run: exact sequence match; **step recall** (multiset overlap ÷
required, so one dropped step in an 8-step chain scores 0.875 not 0); answer
accuracy; failure kind (`skip` / `extra` / `other`); and extra-call count.
`skip` and `extra` are tracked separately because an intervention that says
"never skip" can trade one for the other and look neutral on exact match.

For hierarchical conditions each specialist's calls are flattened in delegation
order, so the metric stays identical to the flat conditions.

### Why the specialist prompt is the layer that matters

The runner records each hierarchical run's full `call_log`, so a missing
required tool can be attributed: if its group was never delegated to, the
coordinator under-delegated; if the group *was* delegated, the specialist
dropped it. On a 15-task diagnostic, **4 of 4 missing tools were dropped inside
a correctly-delegated specialist and the coordinator under-delegated zero
times.** Hence `SUBAGENT_SYSTEM_PROMPT` is where interventions go — and worked
examples naming concrete tools cannot go in the coordinator prompt at all,
since it holds only five `delegate_*` tools.

`DelegateTool` and `build_main_registry` take a `subagent_system_prompt`
parameter (defaulting to the shipped prompt) so conditions can vary it.

## Reproduce

```bash
python examples/chain_task_gen.py --steps 8 --count 60 \
    --trigger-density 0.75 --seed 20260902 --out examples/gen_tasks_8step.json

python examples/intervention_ladder_test.py \
    --tasks examples/gen_tasks_8step.json \
    --conditions baseline instruction fewshot \
                 hierarchical_bare hierarchical hierarchical_fewshot \
    --repeat 3 --workers 10 --max-steps 20 --dump results.json
```

Then analyse in the evaluation project:

```bash
python benchmarks/intervention_ladder/analyze.py results.json
```

About 1,080 agent runs, roughly $8 on `deepseek-chat` with prompt caching.
