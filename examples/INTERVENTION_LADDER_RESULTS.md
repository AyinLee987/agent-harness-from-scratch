# The intervention ladder: what actually fixes silent step-skipping

**Date:** 2026-09-02 · **Model:** `deepseek-chat` · **Registry:** 100 tools (flat) / 5 specialists (hierarchical)

| Artefact | Path |
|---|---|
| Task generator | `examples/chain_task_gen.py` |
| Generated task set | `examples/gen_tasks_8step.json` (60 tasks, 8 steps) |
| Sweep runner | `examples/intervention_ladder_test.py` |
| Statistics | `examples/intervention_ladder_analyze.py` |
| Raw dumps | `intervention_ladder_results.json` (5-step), `intervention_ladder_8step_results{,_part2}.json`, `intervention_ladder_8step_hier.json` |

---

## 1. What this set out to test

The tool-scaling experiments established that tool *count* (6→100) and tool
*description length* (6.5x inflation) produce no measurable degradation, and
that the real variable is **chain length**: at 5+ steps the exact tool-sequence
match rate collapsed to 57% while final-answer accuracy stayed at 100%. The
model was silently skipping steps it judged redundant. Hierarchical routing was
then built as an architectural mitigation (57% → 67%, ~2x LLM round trips).

What was never tested is the cheapest intervention available: **telling the
model not to skip steps.** That gap mattered, because `DEFAULT_SYSTEM_PROMPT`
ends with

> "When you have enough information, respond with a final answer and do not call any more tools."

The shipped prompt was actively instructing the model to do the thing being
measured as a failure. If one paragraph fixes it, both the architectural
mitigation and any planned weight-level work are over-engineering.

## 2. Methodology

### 2.1 What counts as a "step"

A **step** is one required tool call. A task's ground truth is an ordered,
duplicates-allowed list `expect_tool_sequence`; **chain length = its length**.
An 8-step chain requires exactly 8 tool calls in exactly that order. Agent
*turns* are not steps — the agent may reason across several turns, and
`max_steps` (the loop budget, set to 20 here) is deliberately far above chain
length so that running out of budget never masquerades as skipping.

This definition is what makes the metric strict: a chain that computes the
right answer in 7 calls has still failed, because the requirement was 8.

### 2.2 Why the original 21-task set had to be replaced

Test-A (the 21 hand-written 5-step tasks) cannot resolve the effects being
measured, for two independent reasons found empirically:

1. **Run-to-run variance swamps the effects.** Re-running the *unchanged*
   baseline on Test-A scored **71.4%**, against the 57.1% recorded three weeks
   earlier — same prompt, same model, same tasks, 3 tasks flipped to passing
   and none regressed. A 14-point swing with nothing changed.
2. **No headroom.** At a 71.4% baseline only 6 of 21 tasks are broken, so the
   maximum possible improvement is 6 tasks, and each task is worth 4.76
   points.

`PLAN.md` §3 constraint B argued this in advance; §2.2 is the demonstration.

### 2.3 Task construction (`chain_task_gen.py`)

Tasks are **generated by walking a tool type graph**, not written by hand.

**Type graph.** Every tool in `tool_scaling_kit.py` has a known signature, so
tools are indexed by what they consume and produce: `number → number`,
`string → string`, `string → number`, `date → date`, `date → number`,
`date → bool`, and so on. A chain is a random walk through this graph: the
walk holds a current value and its type, and may only take an edge whose input
type matches.

**Seeding.** A chain starts from one of four openings, chosen at random: a bare
number, a small list of numbers consumed by a statistic (which itself plants a
T3 trigger), a text string, or a date.

**Moves.** Each move emits one or two steps and advances the value. Moves are
drawn *by weight* without replacement, from either the trigger pool or the
plain pool depending on a Bernoulli draw against `--trigger-density`.

**Ground truth is executed, never written.** Every tool in the kit is a pure,
dependency-free function, so after choosing a move the generator *calls the
real tool function* and carries the real return value forward. The expected
tool sequence is whatever the walk took, and the expected final answer is
whatever the last call actually returned. **Labelling cost is zero and the
labels cannot drift from the tools' behaviour** — the structural advantage this
setup has over a typical post-training data pipeline (`PLAN.md` §5.5).

**Prompt rendering.** Each step carries a natural-language phrase template
("round it to 2 decimal places", "convert it back to kilograms"). The prompt is
the opening sentence followed by the phrases joined with "then", which keeps
the required sequence unambiguous while reading like the hand-written tasks.

**Output schema** is byte-compatible with `tool_scaling_multi_tasks.json`, plus
an underscore-prefixed `_meta` block (chain length, trigger classes, final
value) that existing scripts ignore.

### 2.4 Trigger classes: enriching toward the failure

A uniformly random chain is mostly steps the model performs correctly, which
starves the measurement of signal. Chains are therefore enriched with the five
redundancy pressures reverse-engineered from the original failure cases
(`PLAN.md` §5.3):

| Class | Definition | How it is planted |
|---|---|---|
| **T1** no-op round | `math_round` on a value already at that precision | Round to the value's *current* decimal precision, verified to be a genuine no-op before the step is accepted |
| **T2** inferable bool | a boolean the model can reason out | `calendar_is_weekend`, `text_is_palindrome`, `encode_is_ascii` |
| **T3** small stat | a sum/count/average over 3–5 single-digit numbers | Planted at the seed |
| **T4** same tool twice | the same tool twice in a row | Emitted as a paired move |
| **T5** identity round trip | `A` then `A⁻¹`, returning to the input | 8 unit-conversion pairs, 3 codec pairs |

Two calibration details that materially changed the corpus:

- **T1 was initially restricted to integer values**, which starved it: any unit
  conversion earlier in the chain produces a float, after which no no-op round
  could be planted. T1 appeared in only 35% of tasks while it was the dominant
  failure in Test-A (14/21). Generalising to "round to the value's own
  precision" — rounding 9.999975 to 6 places is exactly as much a no-op as
  rounding 70 to 0 — brought T1 to 78%.
- **Trigger moves are weight-sampled**, because uniform choice let the
  two-step moves (round trips, doubled tools) dominate the step budget; T5 hit
  82% before weighting.

Resulting corpus: **60 tasks, 8 steps each, 100% carrying at least one
trigger** — T1 78%, T5 73%, T4 62%, T3 32%, T2 18%, across 46 distinct tools.

### 2.5 Conditions

| Condition | Registry | Main prompt | Specialist prompt |
|---|---|---|---|
| `baseline` | flat, 100 tools | shipped `DEFAULT_SYSTEM_PROMPT` | — |
| `instruction` | flat, 100 tools | early-stop clause removed, completeness rule added | — |
| `fewshot` | flat, 100 tools | `instruction` + two worked examples | — |
| `hierarchical_bare` | main + 5 specialists | `MAIN_SYSTEM_PROMPT` | completeness sentence **removed** |
| `hierarchical` | main + 5 specialists | `MAIN_SYSTEM_PROMPT` | shipped `SUBAGENT_SYSTEM_PROMPT` |
| `hierarchical_fewshot` | main + 5 specialists | `MAIN_SYSTEM_PROMPT` | shipped + a worked example |

`instruction` changes exactly one thing relative to `baseline` — everything
before the completeness rule is byte-identical. The few-shot examples use tools
that appear in **no** Test-A task (a divide/round chain, a metres↔feet round
trip) so they demonstrate the *behaviour* rather than the test items; they do
still exhibit the T1 and T5 *patterns*, which is noted as a threat in §6.

For the hierarchical conditions, each specialist's own tool calls are flattened
in delegation order and compared against `expect_tool_sequence` — the identical
metric the flat conditions use, so the comparison stays apples-to-apples.

### 2.6 Localising the skip before intervening — and a confound it exposed

Before adding any prompt to the hierarchical arm it was necessary to know
*which layer* drops the step: does the main agent fail to delegate a sub-task,
or does a correctly-delegated specialist not execute it? The runner records the
full `call_log` (group, delegated sub-task text, tools actually called), so a
missing required tool can be attributed: if its group was never delegated to,
the main agent under-delegated; if the group *was* delegated, the specialist
dropped it.

On a 15-task diagnostic, **4 of 4 missing tools were dropped inside a
correctly-delegated specialist. The main agent under-delegated zero times.**
So the specialist prompt, not `MAIN_SYSTEM_PROMPT`, is the layer any prompt
intervention has to target — and worked examples naming concrete tools cannot
go in the main prompt at all, since the main agent only holds five
`delegate_*` tools and would be shown examples of tools it does not have.

That diagnostic also surfaced a **confound in the original hierarchical
result**: the shipped `SUBAGENT_SYSTEM_PROMPT` already contains a completeness
instruction —

> "call every tool call the task actually requires, even one whose result looks
> like it wouldn't change (e.g. rounding a number that is already at the target
> precision); do not skip a step just because you are confident you already
> know the answer."

The `hierarchical` arm was therefore never a pure architectural intervention.
It carried an anti-skipping rule at exactly the layer where skipping happens,
and no previous measurement separated the two. `hierarchical_bare` removes that
sentence and changes nothing else, which is what makes §4.6 possible.

The specialist few-shot example is written **tool-agnostically** ("take 5,
round it to 2 decimal places, then multiply by 3") because each specialist
holds a different 20-tool slice; naming `math_round` would show `text_agent` a
tool it does not have.

Enabling this required a small, backwards-compatible change to the kit:
`DelegateTool` and `build_main_registry` gained a `subagent_system_prompt`
parameter that defaults to the shipped prompt, so every existing caller is
unaffected.

### 2.6 Metrics

- **Exact sequence match** — called tool names, in order, equal
  `expect_tool_sequence`. Strict and all-or-nothing.
- **Step recall** — multiset intersection of called and expected, over expected
  length. One skipped step in an 8-step chain scores 0.875 rather than 0. Far
  lower variance than exact match, and it isolates *skipping* specifically.
- **Final-answer accuracy** — the answer contains the executed chain's real
  final value.
- **Failure kind** — `skip` (called is an ordered subsequence of expected:
  steps dropped, nothing invented), `extra` (expected is an ordered subsequence
  of called: everything done plus unrequested calls), `other` (wrong tool or
  wrong order), `match`.
- **Extra calls** — count of calls beyond the required multiset. Direct
  measurement of over-correction; on tasks with an exact expected sequence,
  every extra call is over-correction, which is a Test-C signal for free.

Tracking `skip` and `extra` separately is the point: an intervention that says
"never skip a step" can trade one failure for the other and look neutral on
exact match. That is precisely what happened.

### 2.7 Statistics

k=3 trials per task per condition. **The unit of analysis is a task, not a
run** — with 3 trials the per-task pass rate is a continuous score in
{0, ⅓, ⅔, 1}, and conditions are compared as matched pairs over the same 60
tasks. Treating 180 runs as independent would triple-count each task.

Paired bootstrap (10,000 resamples of the per-task deltas) and bootstrap CIs
come from the companion project's `agent_eval.stats`, reused rather than
reimplemented.

## 4. Findings

### 4.1 An abstract rule stops the skipping and creates an equal and opposite failure

`instruction` did exactly what it was told: step recall 0.838 → 0.972,
`skip` failures 55 → 6, both overwhelmingly significant. And it bought
**nothing** on exact match (−0.6pp, p=0.86), because the skips were replaced
one-for-one by unrequested calls: extra calls 185 → 393, `extra` failures
26 → 81. Final-answer accuracy collapsed from 78.9% to 49.4%.

"Never skip a step" is an undirected command. The model complies by calling
more tools everywhere, including where it should not.

### 4.2 Demonstrations are what carry the signal — and this reverses at scale

`fewshot` is the only condition with a significant exact-match gain
(+17.8pp, p=0.0066), and it wins on four of five trigger classes. Its step
recall is statistically indistinguishable from `instruction`'s (0.974 vs
0.972) — the difference is entirely in over-correction control: 217 extra
calls versus 393.

The rule states what not to omit. The worked examples show what a complete
trajectory *is*, which communicates the upper bound as well as the lower one.

**This inverts the five-step conclusion.** On Test-A, `instruction` and
`fewshot` produced *identical per-task results* — 0 discordant pairs — and the
write-up concluded the examples were redundant. At eight steps the instruction
alone is a wash and the examples are the whole effect. Any conclusion drawn
from the 5-step set about which intervention works was an artefact of the
regime, not a property of the intervention.

### 4.3 The 57% → 67% hierarchical routing result does not survive a powered test

At 8 steps, hierarchical routing scores 43.9% against a 38.9% baseline:
**+5.0pp, p=0.52**. On 60 tasks with k=3 — a design with far more power than
the original 21×1 — the improvement is not distinguishable from noise.

It is not worthless: it improves step recall (+0.110, p<0.0001) **without**
damaging final-answer accuracy (+1.7pp, p=0.75) — the only arm that does both.
But it costs 6.87 delegations per run, each a full subagent invocation, and it
is beaten on exact match by a paragraph of prompt text that costs nothing.
§4.6 goes further: the recall gain is not the routing's at all.

### 4.6 The routing contributes nothing; its prompt does all the work

`hierarchical_bare` is `hierarchical` with one sentence deleted from the
specialist prompt and nothing else changed. It scores:

| | exact match | step recall | answer accuracy |
|---|---|---|---|
| flat baseline | 0.389 | 0.838 | 0.789 |
| **hierarchical_bare** | **0.333** (p=0.35) | **0.867** (p=0.227) | 0.728 (p=0.37) |
| hierarchical | 0.439 | 0.949 | 0.806 |

Stripped of that sentence, routing does **not** significantly reduce skipping
(+0.029, p=0.227, against +0.110 for the same architecture with the sentence),
its `skip` failures jump back from 20 to 52 — essentially the flat baseline's
55 — and its exact match falls *below* doing nothing at all.

So the entire measured benefit of the hierarchical architecture came from a
single anti-skipping instruction that happened to be embedded in
`SUBAGENT_SYSTEM_PROMPT`, not from shrinking the main agent's tool surface from
100 tools to 5. The architecture on its own buys 7 delegations per run and no
measurable accuracy.

This is the strongest result here, and it was only findable because §2.6 asked
which layer the skip happens in before trying to fix it.

### 4.7 Routing and demonstrations do not stack

`hierarchical_fewshot` — the worked example added to the specialist prompt,
which §2.6 established is the layer that drops steps — scores **0.411
(+0.022, p=0.78)**, statistically indistinguishable from both `hierarchical`
(0.439) and the baseline. Its step recall (0.943) is if anything a hair below
plain `hierarchical` (0.949).

The reason is visible in the failure composition: under hierarchical routing,
skipping is already handled (20–22 `skip` failures out of 180), and what
remains is `other` (36–39) and `extra` (45) — errors introduced by the
delegation layer itself, including runs that delegate 20 times to complete an
8-step chain. A specialist-level prompt cannot fix a coordination failure. The
same demonstration that is worth +17.8pp in the flat setting is worth nothing
here, because it addresses a bottleneck that routing has already moved.

### 4.4 Exact-sequence match alone would have misled us

`fewshot` wins by 17.8 points on the headline metric while being 13.3 points
*worse* than doing nothing on final-answer accuracy. `hierarchical` is the
only intervention that leaves answers intact.

At five steps this dimension had no resolving power at all — answer accuracy
was 100% in every condition. It only becomes informative once chains are long
enough for errors to actually corrupt the result.

### 4.5 The failure changes character with chain length

At five steps every failure in every condition was a `skip` — zero wrong-tool,
zero wrong-order, zero extra calls, and answer accuracy was always 100%. At
eight steps the baseline already shows 29 `other` and 26 `extra` failures and
answer accuracy drops to 78.9%.

The clean "silently drops a redundant step while still getting the right
answer" phenomenon is a five-step effect. Past that, chains degrade in several
ways at once — which matters for `PLAN.md`, whose Stage 2 pipeline discards
everything that is not a clean skip.

## 5. Consequences for the post-training plan

1. **The target moved.** The number to beat is no longer 57%; it is `fewshot`
   at 56.7% exact match, and the constraint is answer accuracy ≥ 78.9%. No
   intervention tested achieves both.
2. **The real problem is now well posed.** Every intervention that *states a
   rule* stops the skipping — that part is easy, and three different phrasings
   do it. None stops it *without* inducing unrequested calls or degrading
   answers. What is needed is something that judges whether a specific step is
   required at a specific point, which is exactly what a static rule cannot
   express and a learned gate could.
5. **Architecture was not the lever.** The one architectural intervention in
   the ladder contributes nothing once its prompt is controlled for (4.6).
   Any future comparison against "the hierarchical baseline" has to specify
   which specialist prompt it means.
3. **Over-correction is not a hypothetical training risk.** `PLAN.md` §8 lists
   it as the largest risk of the training arm. It appeared first, and severely,
   in the *prompt* arm. Test-C is required for every rung of the ladder.
4. **Stage 2's bucket filter needs revisiting** at 8 steps, where `other` and
   `extra` failures are a third of the total rather than zero.

## 6. Threats to validity

- **Few-shot examples are pattern-adjacent.** They use tools absent from every
  task set, but they do demonstrate the T1 and T5 patterns, which are the two
  largest trigger classes here. Some of the `fewshot` gain on those classes is
  in-distribution. An honest follow-up would hold out the demonstrated
  patterns entirely.
- **`instruction` changes two things at once** — it removes the early-stop
  clause *and* adds the completeness rule. Which half does the work is
  untested; the ablation is nearly free and has not been run.
- **Single model.** All results are `deepseek-chat`.
- **Generated tasks are synthetic and occasionally absurd** ("base64-encode it,
  decode it, encode it, decode it"). That is the redundancy pressure being
  tested, but it is not natural user traffic.
- **The `hierarchical_bare` ablation removes one sentence, not the concept.**
  It shows the shipped prompt carries the benefit; it does not prove no
  specialist prompt could make routing pay off.
- **The delegation layer was not itself tuned.** `MAIN_SYSTEM_PROMPT` was held
  fixed across all three hierarchical arms, so the `other`/`extra` failures
  4.7 attributes to coordination were never targeted by any intervention.
- **The 5-step numbers in §4.2 and §4.5 come from k=1 runs** on 21 tasks and
  should be treated as indicative only. That is the point of §2.2.

## 7. Reproduce

```bash
python examples/chain_task_gen.py --steps 8 --count 60 \
    --trigger-density 0.75 --seed 20260902 --out examples/gen_tasks_8step.json

python examples/intervention_ladder_test.py \
    --tasks examples/gen_tasks_8step.json \
    --conditions baseline instruction fewshot hierarchical \
    --repeat 3 --workers 10 --max-steps 20 --dump results.json

python examples/intervention_ladder_analyze.py results.json
```

Roughly 720 agent runs; about $6 on `deepseek-chat` with prompt caching, an
hour of wall clock at 10 workers.
